## 2. The extension returns the app URL, and Studio saves it with the topic

An **invoker** is the configured instance of an extension in a workspace. KA already declares a `serviceUrl` Setup field. Deployment automation can supply its value, and the extension's `HostingResource` still reads the saved field from the current invoker when Studio calls it. The sample can teach this field directly with a manual Setup save. The response is `{"payload":{"hostingUrl":"https://your-agent.example.com/"}}`. The extension endpoint is registered in `KnowledgeAgentAppliance`, KA's JAX-RS application. Studio calls `GET <routed invoker base>/rest/hostUrl`. The returned URL is the iframe app entry point.

In the inspected Studio path, changing the topic's selected invoker triggers discovery from the invoker's live route. Studio then saves the extension's routing base as `invokerUrl` and the returned app address as `hostUrl`. The server persists both on the topic and sends them back as part of the agent state. Saving only the invoker's Setup attribute can leave a topic on the old URL. Studio's code suggests clearing the invoker selection in the form, reselecting it, waiting for discovery, and saving once. Saving the cleared selection removes the assignment. Verify the exact refresh steps in the workspace UI before documenting them as proven.

- **KA evidence.** Catalog `knowledge-agent/src/main/java/app/krista/global/knowledgeagent/KnowledgeAgentExtension.java:45–53,91–110`, `api/HostingResource.java:19–39`, and `api/KnowledgeAgentAppliance.java:14–25`, with `api/` under the same Java package. KA's resource literally appends `/` to the saved string. The sample should document the accepted URL form and preserve a supplied app path.
- **Studio evidence.** `webmono/projects/StudioNgNew/src/app/services/core/http/apis/agentSetup/ReqGetHostingUrl.ts:5–17`, `services/feature/workspace/agent-setup/agent-setup-http.service.ts:47–63` under the same `src/app/` root, and `modules/editors/workspace/content/tabs/2-channels/details/ws-channel-agentic-guide/ws-channel-agentic-guide.component.ts:284–304,320–394`. ## 3. Keep the browser launch context and KSDK request identity distinct

The KA UI receives a parent-window `postMessage` after the iframe loads. The receiver reads `workspaceId`, `invokerUrl`, `emailId`, and an account ID or session field, and also handles `agentId`. KA forwards its context to its own backend. That backend looks up the extension callback it previously registered for the workspace and then calls `/rest/session/validate`. Its callback and registration machinery belong to KA's application. The saved topic `hostUrl` is how Krista finds the app, and the extension callback is how the app reaches code running inside Krista.

The inspected KA receiver prefers `accountId.id` and calls the value a session ID. The extension's endpoint then passes it to `AccountProvider.getAccount`, which loads an account by ID in the request's workspace and requires an authenticated extension request. This is evidence of a scoped account lookup. Establish how the sample receives a platform-authenticated user context before selecting the live call path. The parent message starts the UI flow. The runtime identity should determine the account read through KSDK.

### Identity probe · admin session · 2026-11-18

The user approved installing the disposable identity probe and testing their current admin session, with the launch credential confined to Solution Labs. Studio accepted identity probe 1.0.1, provisioned it as a managed invoker, and discovered its bundled URL for the dedicated test topic. The client profile supplied an independent expected display name. Inside the real iframe, the same-invoker greeting request without a credential returned HTTP 401 and neither greeting field. The request with the launch credential also returned HTTP 401. This first run did not establish KSDK caller binding. No credential values were recorded. The probe is being instrumented to identify the first failing authentication stage.

Identity probe 1.0.2 added fixed diagnostic stages without recording token or response contents. On a cache-bypassing reload, the same-invoker response identified the no-credential request as `AUTHORIZATION_HEADER_ABSENT`. The credentialed request reached the callback with a Bearer header of the expected shape and then failed with `CALLBACK_FAILED`. That result places the failure after header and credential shape validation. It does not yet identify whether the failing operation was the outbound IAM call or the subsequent KSDK work.

Identity probe 1.0.3 narrowed the failure to `ACCOUNT_STATUS_READ / RUNTIME`. Its code reaches this stage only after IAM says the token is active, the token contains the runtime workspace, and the workspace-scoped lookup returns an account ID. The KSDK's `AccountImpl.isBlocked()` and `ModifiableAccountImpl.isBlocked()` both throw `UnsupportedOperationException`. Version 1.0.4 removes that unsupported probe-only call. It still requires an active access token, the runtime workspace membership, a resolved account ID, a matching person subject, and a bound KSDK context.

**Admin-session result.** Deployed identity probe 1.0.4. The authenticated browser request to `GET <routed invoker base>/rest/greeting` returned HTTP 200 with `CONTEXT_BOUND`. The same request with credentials omitted returned HTTP 401 and neither greeting field. Studio discovery continued to populate the hosting URL independently of the end-user greeting request.

The iframe accepted the JWT only from its expected Krista parent and sent it as a Bearer header to the same-invoker route on the Solution Labs extension origin.
